# Project-Build Pipeline Evaluation — 2026-07-07

**Scope:** end-to-end evaluation of the MARVIN build pipeline: the router (`context/project-build-pipeline.md`), the nine pipeline skills, the two agent contracts, the four enforcement scripts, and the five issues shipped through it on 2026-07-06/07 (#580, #581, #586, #491, #498 via PRs #587-#596).
**Method:** read every design doc and script directly; pulled GH issue/PR/diff evidence and the agent-runs ledger via subagents; re-ran the five acceptance suites locally; verified commit ordering with `git log --follow`. Every empirical claim below cites a file, PR, or run id. Where I could not verify, I say so.
**Not committed. Findings become issues only after Matt reviews.**

## Verdict per lens

### 1. Design critique: sound core, one honor-system seam

The architecture is genuinely good. One invariant (acceptance tests committed PENDING on `main` before implementation, never weakened), a router that only routes, skills that reference rather than fork each other's procedures (spec-up Step 4 reuses write-a-prd Step 7.5; spec-wave orchestrates spec-up/spec-dev unchanged), and a layered defense: shape validators (deterministic) under Codex (semantic) under the human gate. The `xfail(strict=True)` pending convention is exactly right: a pending test that accidentally starts passing fails the suite, so false-greens self-report.

The main structural weakness: **every enforcement layer except CI-pytest is executed by the same model session that is being policed.** The `check_acceptance_integrity.py` guard, the Codex gate, the ledger update, and the `cross_review` verdict are all run and recorded by the launching session, per SKILL.md instructions. Nothing machine-enforces any of it at merge time. CI (`.github/workflows/ci-tests.yml`) runs `pytest tests/ -q` on PRs touching `scripts/**` or `tests/**` and nothing else: a weakened assertion passes CI green, a deleted test passes CI green, and a PR touching only `skills/*.md` runs no CI at all. The one invariant is real in the artifacts (see lens 2) but its enforcement is procedural. Concrete bypass routes, in rough order of ease:

1. **Skip the guard.** spec-dev says to run the weaken-check "before the second-model review" (skills/spec-dev/SKILL.md:243-256), but no hook, CI job, or branch protection verifies it ran. A session under context pressure that forgets it leaves only Matt's eyeball review.
2. **Weaken outside the acceptance file.** The guard compares only the targeted acceptance file(s). `conftest.py` fixture edits, `pyproject.toml` / `pytest.ini` `addopts` (`--deselect`, `--ignore`), `collect_ignore`, or editing a helper module the test imports are all invisible to it. #588 covers data-flow indirection inside the file; config-level de-selection is not filed anywhere I found.
3. **Weaken at authoring time.** A lazily-satisfiable suite that gets approved is forever "not weakened." The Step 0 lazily-satisfiable guard, the verify-red-today rule (spec-wave Step 2), and Codex coverage review mitigate this, and the golden-value shape lint (`validate_spec_up_issue.py:66-85`) explicitly checks shape only ("run cmd -> exit 0 still passes", its own docstring).
4. **The amendment path is unrealistic, so amendments route around it.** spec-dev says new/changed acceptance tests go "through /write-a-prd (the contract is amended there, with a logged reason)" (skills/spec-dev/SKILL.md:109-111). In practice PR #592 changed seed args in two committed #577-era suites (`test_agent_runs_writepath_integrity.py`, `test_agent_runs_writepath_lock_unit.py`) in-slice, disclosed in the PR body, cleared by Codex. That was the right engineering call, and it proves the sanctioned path is too heavyweight to be used. Note the irony: the #491 guard, merged two hours later, would classify those exact edits as WEAKENED (body change on a committed test). The pipeline has no lightweight, auditable amend procedure, so legitimate amendments are indistinguishable in kind from the attack the guard exists to block.

Redundancy/over-engineering: modest. The skills are long (spec-dev 333 lines, harden 559) but cross-reference instead of duplicating, which is the hard part. harden's 559 lines with two separate `## Rules` sections (lines 512, 543) is the one file that has grown past coherent. For a single-user workspace the four-gate process is heavy per issue, but the ledger now prices that heaviness ($0.60 to $8.31 per run, below), which is the correct way to decide if it's worth it. It looks worth it: #491's $8.31 bought a guard plus four real bug fixes.

### 4. vs. industry best practice: ahead on contract discipline, behind on machine enforcement

**Where it leads.** Committing executable acceptance tests to `main` before implementation, with strict-xfail so accidental passes fail loudly, is ATDD done more rigorously than most industry teams manage (typical practice: criteria live in the ticket and tests arrive with the implementation, written by the same person, gradeable by nobody). The test-author/implementer independence "won across pipeline stages" (spec-dev line 129-133) is the real ATDD idea, correctly implemented. The AST-level anti-tamper guard has no common industry equivalent; the closest analogues are codeowner-protected test directories and Meta-style "do not modify" test annotations, and this is more precise than either. Dual-model adversarial review predates industry consensus but matches emerging practice (reviewer model != author model), and #491 is a documented case of it paying. Per-run token/duration/USD costing of agent work is ahead of nearly everyone. The invariant lens in spec-up Step 3 (derive a criterion the sequential happy path cannot satisfy: DB constraint + concurrency test) is a genuinely sophisticated move most checklists lack.

**Where it lags proven practice.**
- **Branch protection / required checks.** Industry's first move for an inviolable invariant is a required CI status check plus branch protection. The pipeline's most important guard runs only by procedural instruction. A ~20-line CI job (diff acceptance files against merge-base, run `check_acceptance_integrity.py --old/--new` on each) would convert the invariant from "the session is instructed to" into "the merge button is gated."
- **Mutation testing.** The lazily-satisfiable guard and Codex tautology review are manual proxies for what mutmut/cosmic-ray do mechanically: prove the suite fails when the behavior is broken. spec-wave's "verify it is red today" is the right instinct, one mutation per suite; mutation testing generalizes it.
- **Living documentation / machine-linked plain English.** The dual-layer format is BDD's insight (Gherkin: the plain-English line IS the executable spec). Here the plain layer is prose in issue bodies and docstrings; `validate_accept_body.py` checks its shape, not its agreement with the assertions, so the two can drift after approval and nothing notices.
- **Diff coverage gates.** No check that new implementation lines are exercised by any test; industry norm is diff-coverage >= N% as a required check.
- **Suite lifecycle policy.** "The acceptance suite is the regression set" and "done is pending count zero" (spec-dev line 305-309) is right, but there is no tiering, runtime budget, or flake policy for when the cumulative suite gets slow. Cheap to fix at this scale, expensive later.
- **Review artifacts.** Industry review culture keeps the review attached to the PR. Codex verdicts here live in a one-token ledger field plus session-log prose; no reviewable transcript survives (I could not independently verify #491's four rounds for exactly this reason).

### Nitpicks (not defects)

- `test_must_surface.py`'s module docstring still says "This whole module is xfail(strict=True)" though the marker was removed on flip (stale comment).
- `test_accept_body_wired_into_authoring.py`'s token-window matching (RUN/BLOCK/ORDER within 300 chars) is clever but brittle both ways: a validly reworded instruction fails; three tokens coincidentally near a mention passes. Fine as a tripwire, don't grow the pattern.
- The skills-audit note's harden trigger criticism ("check test coverage" fires the full audit) is about discovery, not pipeline correctness; agreed but out of scope here.
- `test_check_acceptance_integrity_unit.py` was born required with the implementation (never PENDING). This is consistent with the design (implementers may add unit tests) but worth knowing when reading the git history: not every test file in a feat PR was pre-committed.

### Genuinely good (call these out, they are not accidents)

- **The invariant held empirically on all three test-backed issues**, verified in git history, with clean marker-only flips in every merged diff (PRs #592, #595, #596).
- **The cross-review gate earned its cost**: 4 distinct false-allows closed on #491, each with a named regression test; and the #581 review correctly distinguished alignment from weakening.
- **The guard's own design quality**: AST-based (comment/whitespace immune), asymmetric decorator rule (removal allowed, addition/reorder/downgrade blocked), positive control in the suite so a constant-fail stub can't pass (`test_entry_present_and_pending_passes`, `tests/test_acceptance_integrity.py:323-332`), and an honest SCOPE LIMIT docstring with the follow-up filed (#588).
- **Anti-false-green discipline in the suites**: blocked cases assert exit-nonzero AND keyword AND test name, so a missing script can't accidentally satisfy them (suite docstring, lines 41-47). This is the #412/#483 lesson, learned and applied.
- **Ledger cost hygiene**: 100% of terminal marvin runs carry the tuple or an explicit waiver; zero stale `running` entries across 53 runs.
- **Self-referential dogfooding works**: the pipeline shipped its own enforcement (#491, #498, #581) through itself, and the follow-ups it couldn't cover became issues (#588, #593) per the follow-ups-become-issues rule, not prose.

## Highest-leverage improvement

**Move the invariant's enforcement from procedure to a required CI check.** One workflow job: on every PR, diff acceptance files against the merge base and run `check_acceptance_integrity.py --old/--new` on each changed one (plus flag conftest/pytest-config changes alongside them, finding 6). The guard already exists and is well-tested; only its execution is voluntary. This single change closes findings 1 and most of 6, makes finding 5 urgent enough to force the amendment-path design, and converts the pipeline's core promise from "the session was instructed to check" into "the merge was physically gated." Everything else on the list is smaller than this.
