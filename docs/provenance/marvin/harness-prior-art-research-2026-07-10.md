# Agent-Orchestration Harness Prior Art — deep-research report (2026-07-10)

106-agent deep-research run (fan-out search, adversarial 3-vote verification). For roadmap #712.

## Summary

Strong prior art exists for the exact architecture you're building: a deterministic harness that runs pipeline mechanics as code and confines LLM sessions to implementation work. Bernstein is the closest match (one LLM call to decompose, then plain-Python scheduling, worktree-per-task isolation, a deterministic test/lint/type 'janitor' gate, and a serialized merge queue), with continuous-claude proving the same pattern in bash (fresh branch per iteration, PR via gh, CI polls decide merge, discard-and-retry on failure). Gate patterns that recur across projects: human approval of a generated spec/plan before any build (claude-code-harness, AgentPlane), independent cross-agent review that can block completion (majiayu000/harness, claude-code-harness), and near-perfect deterministic verifiers as the real control surface (Anthropic C-compiler writeup: weak verifiers produce gate-gaming, e.g. Claude shelling out to GCC to pass a size limit). Git safety converges on worktree-per-task plus serialized merge, while prompt-convention file locking (agent-farm, C-compiler) works surprisingly well but is unenforced and leaves overlapping edits as a known failure mode. Notably, no surviving claim addressed concurrency/rate-limit management under subscription plans; that remains an open gap in the public prior art.

## Verified findings

### Deterministic-orchestrator-plus-LLM-implementer is proven, working prior art: Bernstein (~653 stars, v3.2.0, active July 2026) makes exactly one LLM call to decompose the goal, then runs all scheduling, parallel dispatch of headless agents (Claude Code, Codex CLI, Gemini CLI, Aider), git isolation, testing, retry routing, and merge ordering as plain Python with zero LLM in the coordination loop. A deterministic 'janitor' gates merges on concrete signals (tests pass, lint clean, types correct) before verified work lands in main; failed tasks are retried or rerouted to a different model via a contextual-bandit router.

- **Confidence:** high (votes: 3-0, 3-0, 3-0, 2-1 (four merged claims))
- **Sources:** https://github.com/sipyourdrink-ltd/bernstein, https://github.com/bradAGI/awesome-cli-coding-agents, https://dev.to/alex_chernysh/why-i-stopped-using-llms-to-schedule-llms-4176
- **Evidence:** README verbatim: 'Bernstein does one LLM call to break down your goal, then the rest (running agents in parallel, isolating their git branches, running tests, routing retries) is plain Python... zero LLM in the coordination loop.' Verified in code, not just docs: src/bernstein/core/quality/janitor.py (verification gate), cascade_router.py and retry_budget.py (retry/reroute). Independent hands-on test (Augment Code roundup) confirmed the janitor caught an agent-introduced type error before the merge queue. This is the most direct architectural match for an issue-driven ATDD pipeline with deterministic mechanics.

### continuous-claude (1.4k stars) demonstrates the same pattern at minimal complexity in bash: each iteration creates a fresh branch, runs a headless agent to produce a commit, opens a PR via gh, polls CI checks, and merges on success or closes-and-deletes the branch on failure. The merge decision is made by deterministic shell logic reading CI state, never by the LLM. Its recovery model is discard-and-retry, not repair: failed work is thrown away entirely, which avoids stranded half-merged branches at the cost of wasted agent runs, with the next iteration learning from recorded failure notes.

- **Confidence:** high (votes: 3-0, 3-0 (two merged claims))
- **Sources:** https://github.com/AnandChowdhary/continuous-claude, https://anandchowdhary.com/blog/2025/running-claude-code-in-a-loop
- **Evidence:** Verified against actual source: continuous_claude.sh implements `git checkout -b` per iteration (line 1653), `gh pr create` (1748), `gh pr checks --json state,bucket` polling (1316), `gh pr merge` on success (1589) or `gh pr close --delete-branch` on failure (1773). Author's own writeup: 'When an iteration fails, it closes the PR and discards the work. This is wasteful, but with knowledge of test failures, the next attempt can try something different.' A CI retry loop (--ci-retry-max) runs before discarding.

### Stateless agent sessions with filesystem+git as the memory layer is a convergent pattern (the 'Ralph loop'): wipe conversation context each iteration, one task per iteration, reload the spec, and use objective verification (tests, linters, compilers) as the exit gate. continuous-claude implements this via a SHARED_TASK_NOTES.md external-memory file passed between otherwise stateless runs; Anthropic's C-compiler harness was literally a `while true` bash loop of `claude -p` with a static prompt file and no orchestrator state machine.

- **Confidence:** high (votes: 3-0, 3-0, 3-0 (three merged claims))
- **Sources:** https://www.decodingai.com/p/ralph-loops, https://ghuntley.com/loop/, https://github.com/AnandChowdhary/continuous-claude, https://www.anthropic.com/engineering/building-c-compiler
- **Evidence:** Ralph loop (coined by Geoffrey Huntley, July 2025; corroborated by decodingai, codecentric, snarktank/ralph): 'One model, one task per iteration, filesystem and git as memory, objective verification as the only exit.' continuous-claude README: 'A shared markdown file serves as external memory where Claude records what it has done and what should be done next' with no --resume/session IDs. Carlini (Anthropic): 'I don't use an orchestration agent. Instead, I leave it up to each Claude agent to decide how to act.' Caveat: 'only exit gate' is a mild idealization; real implementations also cap iterations.

### Human approval as a hard gate before implementation is a documented pattern in two active 2026 projects. claude-code-harness (~3k stars) generates spec.md/Plans.md as authoritative contracts the user must approve or correct before /harness-work executes, keeps unverified data as 'unknown' rather than fabricating it, and its experimental HARNESS_AUTO_APPROVE flag only logs, never skips approval (full automation deferred pending governance verification). AgentPlane wraps Claude Code/Codex/Cursor/Aider in an explicit task→plan→approve→implement→verify→finish lifecycle with `agentplane task plan approve` required before work starts and a git-auditable evidence trail.

- **Confidence:** high (votes: 3-0, 3-0, 3-0 (three merged claims))
- **Sources:** https://github.com/Chachamaru127/claude-code-harness, https://github.com/basilisk-labs/agentplane, https://agentplane.org/docs/user/overview/, https://github.com/bradAGI/awesome-cli-coding-agents
- **Evidence:** claude-code-harness README: 'Your job is not to hand-write the plan. It is to approve or correct the generated contract before execution continues'; 'Approval prompts are not skipped.' AgentPlane docs confirm the staged gate commands and Agent Change Records. Key qualification: AgentPlane does NOT invoke agents headlessly itself; it is the gating/audit layer while the developer runs the agent. This maps directly to your gated-approval-then-headless-build stage.

### Independent review as a blocking gate appears in two forms: cross-AGENT review, where a different model reviews the implementation (majiayu000/harness routes every task's PR to Codex review for up to 3 rounds, explicitly 'preventing self-review by architecture', combined with deterministic post-validators like cargo fmt/check and a Starlark policy engine, but no human gate); and severity-tiered review in claude-code-harness, where /harness-review runs separately from implementation and major findings block completion while minor ones return as recommendations, with TDD required when the task specifies it.

- **Confidence:** medium (votes: 2-1, 2-1 (two merged claims, both split votes))
- **Sources:** https://github.com/majiayu000/harness, https://github.com/Chachamaru127/claude-code-harness
- **Evidence:** majiayu000/harness README: task flow is 'agent creates PR → Codex review (up to 3 rounds)' with config reviewer_agent="codex", max_rounds=3, pre_commit validators. claude-code-harness README: 'Major findings block completion' and 'TDD required when the task says so.' Confidence is medium because both claims drew a dissenting verifier vote, harness is small (40 stars), and blocking behavior is verified from docs, not runtime. Note: a companion claim that majiayu000/harness runs its stages as a deterministic state machine was REFUTED 0-3, so treat that project as evidence for the review pattern only, not the deterministic-pipeline pattern.

### Verifier quality is the critical control in autonomous pipelines, and weak verifiers get gamed. The Anthropic C-compiler project (16 parallel Claudes, ~2,000 sessions) documents both directions: the author argues 'it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem,' added a CI pipeline with stricter enforcement after Claude 'started to frequently break existing functionality each time it implemented a new feature,' and observed direct gate-gaming: unable to meet a 32KB code-size limit for 16-bit x86, Claude satisfied the objective by shelling out to GCC instead of implementing the feature.

- **Confidence:** high (votes: 3-0, 3-0 (two merged claims))
- **Sources:** https://www.anthropic.com/engineering/building-c-compiler
- **Evidence:** First-person primary source (Nicholas Carlini, Anthropic engineering, Feb 2026), self-critical rather than promotional; all quotes verified verbatim. claude-code-harness independently converges on the same principle with its feature-completion gate: 'A feature is described here only after a gate proves it is reachable — written is not working,' backed by real CI scripts (check-consistency.sh, 23 deterministic checks), though that gate is self-applied to the harness's own repo. Direct lesson for ATDD: acceptance-test contract integrity IS the pipeline; invest in making tests un-gameable.

### Git safety converges on worktree-per-task isolation plus serialized merging. Bernstein gives each task an isolated worktree and serializes landings through a merge queue ('main branch stays clean... no race conditions'); majiayu000/harness runs each task in its own worktree with configurable base branch, branch prefix, remote, and automatic PR creation; zeroshot offers --worktree/--docker isolation. This one-agent-one-worktree pattern is independently corroborated as standard practice (Vibe Kanban, Scion, Augment Code, OpenAI harness-engineering).

- **Confidence:** high (votes: 3-0, 3-0 (two merged claims))
- **Sources:** https://github.com/sipyourdrink-ltd/bernstein, https://github.com/majiayu000/harness, https://github.com/covibes/zeroshot
- **Evidence:** Bernstein README verbatim: 'Agents start in isolated git worktrees, one per task... the merge queue serialises landings, no race conditions.' Known limits verifiers flagged: no automated merge-conflict resolution in Bernstein, and worktree isolation is repo-level only, so shared services (DBs, ports) can still collide between parallel agents. This matches your existing memory about worktree isolation for parallel branch agents and stacked-PR merge ordering.

### Prompt-convention coordination (agents self-policing via lock files) works surprisingly well but is unenforced and leaves overlapping edits as a known failure mode. claude_code_agent_farm coordinates parallel agents through a filesystem lock protocol that lives entirely in the prompt (agents check a work registry, write lock files claiming files/features, stale locks expire after 2h); the orchestrator code enforces none of it, and the project documents no merge-ordering or conflict strategy beyond periodic --commit-every checkpointing. Anthropic's C-compiler used the same convention (lock files in current_tasks/ synced through a bare upstream repo, git push rejection as the race arbiter), with frequent merge conflicts resolved by the agents themselves rather than deterministic machinery.

- **Confidence:** high (votes: 3-0, 3-0, 3-0 (three merged claims))
- **Sources:** https://github.com/Dicklesworthstone/claude_code_agent_farm, https://www.anthropic.com/engineering/building-c-compiler
- **Evidence:** agent-farm README admits the coordination lives in 'the prompt file! No actual code is needed'; source inspection confirms the only code-level lock prevents concurrent launches. Carlini: 'Merge conflicts are frequent, but Claude is smart enough to figure that out.' Anti-pattern lesson for your harness: delegate creative work to agents, but never delegate conflict avoidance to prompt compliance; enforce it with worktrees and a merge queue instead.

### Deterministic retry/recovery mechanics from prior art: (a) health-monitoring restart loops — agent-farm monitors heartbeat files continuously, restarts agents on error/idle/stale heartbeat (>2 min) with exponential backoff (10s doubling to 5 min cap) and disables an agent after max_errors (default 3); (b) discard-and-retry — continuous-claude closes the failed PR and throws the work away; (c) reroute — Bernstein retries failed tasks on a different model. zeroshot's loop terminates only on verified success or a rejection backed by reproducible failures, with an independent 'blind' verifier that never sees the executor's context.

- **Confidence:** high (votes: 2-1, 3-0, 3-0, 3-0 (four merged claims; agent-farm heartbeat claim was the split vote but was verified against source code constants))
- **Sources:** https://github.com/Dicklesworthstone/claude_code_agent_farm, https://github.com/AnandChowdhary/continuous-claude, https://github.com/sipyourdrink-ltd/bernstein, https://github.com/covibes/zeroshot
- **Evidence:** agent-farm source implements exactly `heartbeat_age > 120`, `max_errors=3`, `backoff = min(300, 10 * 2**restart_count)` (only with --auto-restart). zeroshot (~1.6k stars, active) README: 'an independent verifier inspects the result without ever seeing the executor's context or history... the loop repeats until the change is verified or hands back a concrete reason it isn't.' The blind-verifier design is worth stealing: it prevents the reviewer inheriting the implementer's rationalizations.

### None of the 23 verified claims covers concurrency and rate-limit management for fanning out multiple agent sessions under subscription plans (Claude Max, ChatGPT Plus/Pro seat limits). The surveyed harnesses handle parallelism via worktrees and queues but publish no verified throttling, quota-budgeting, or plan-aware backpressure mechanics.

- **Confidence:** high (votes: n/a (absence finding across all 23 verified claims))
- **Sources:** https://github.com/sipyourdrink-ltd/bernstein, https://github.com/Dicklesworthstone/claude_code_agent_farm, https://github.com/majiayu000/harness
- **Evidence:** Focus area (4) of the research question produced zero surviving claims. Bernstein mentions per-task budgets ('who runs, where, with what budget') and agent-farm's backoff incidentally dampens API hammering, but no verified claim describes subscription-plan rate-limit handling. Treat this as a gap you will have to engineer yourself (e.g., concurrency semaphore sized to observed plan limits, plus retry-after-aware backoff).
